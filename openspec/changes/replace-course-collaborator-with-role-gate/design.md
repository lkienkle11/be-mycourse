## Context

See proposal.md - Why. Relevant current-state facts this design builds on:

- `internal/authorization` (migration `000034`, committed in `19fc149`) is fully implemented and migrated: `authorization_actions`, `authorization_grants`, `authorization_role_actions`, `authorization_role_bindings`, all currently 0 rows, zero registered `PolicyProvider`s. `GormGrantRepository.ListActive` already merges direct grants with role-expanded grants (`roleExpandedGrants` + `mergeGrants`); `Authorizer.authorize`/`matchingGrantIDs` already decide purely on `domain.Grant{ActionName, Effect}` and never see a role name — this change's "never gate on role name" rule is already satisfied by the existing decision path and only needs to be satisfied by *new* code this change adds.
- Course access today: `requireCourseAccess` (`internal/course/infra/repo_access.go`) treats `courses.owner_user_id == userID` as an implicit OWNER, else looks up a `course_collaborators` row for `(course_id, user_id)` and trusts its `role` column. `requireOwnerAccess` then does `if access.Role != domain.CollaboratorRoleOwner`, the exact role-gate pattern this change forbids. `requireEditorAccess` is currently a passthrough to `requireCourseAccess` (any active collaborator, OWNER or EDITOR, passes) — meaning today there is effectively no EDITOR-only action, only "any collaborator" vs. "OWNER only".
- `course_collaborators` also backs a read-only listing feature (`ListCollaborators`, `repo_collaborators.go`) that joins to `users`/`media_files` for display, and an "instructor candidates" query that excludes existing collaborators (`instructorCandidatesBaseSQL`). These are read concerns, not access-control concerns, and can be served by joining `authorization_role_bindings` instead once it holds the data.
- `internal/authorization/application/grant_service.go` already exists as the write path for direct grants (`Create`/`Revoke`/`ReplaceMany`), gated by `PolicyProvider.CanManageGrants`. The new role-binding management write path (`authorization/role-binding-management`) follows the same authorization pattern: an issuer may assign/revoke a binding on a resource only if `CanManageGrants` says so for that resource (and, for a wildcard assignment, for that resource type as a whole).
- The prior Course integration attempt touched ~19 files with no single seam (see `revert-course-authorization-extension/proposal.md`). This design's central goal is collapsing every course access check behind one seam so a future engine change again touches one file, not many.
- This change is implementation work under `AGENTS.md`'s Implementation Workflow Rules, which mandate reading the complete project `.context` folder and every `.ai/skills` file, and using `memory-bank-cli` (`memory_bank_read_all`, then `activeContext.md`/`progress.md`/verbatim `lastResponse.md` per turn) before and during task work. Task group 0 in `tasks.md` tracks this explicitly so it is not skipped or done only partially, as happened on the first pass at this change.

## Goals / Non-Goals

**Goals:**
- One seam (`requireCourseAccess`/`requireEditorAccess`/`requireOwnerAccess` in `repo_access.go`, or their direct replacement) is the only place in `internal/course` that talks to `Authorizer`. No other file compares a role name.
- Cutover is behavior-preserving: OWNER keeps doing everything it does today, EDITOR keeps doing everything it does today (i.e. "any active collaborator" per the current passthrough), until a product decision later actually differentiates them using the new engine's redefinition capability.
- Course owner access does not require a stored role-binding row — it is derived the same way it is today (`courses.owner_user_id == userID`), just expressed as a synthesized OWNER grant at decision time instead of a special-cased early return.
- The wildcard (`authorization/role-binding-wildcard`) and the management write path (`authorization/role-binding-management`) are resource-type-agnostic additions to `internal/authorization`, usable by any future `PolicyProvider`, not Course-specific.

**Non-Goals:**
- No change to what OWNER/EDITOR can actually do today (that redesign, if wanted, is separate future work once the role gate is live).
- No production backfill or migration strategy — this change's backfill plan is dev-only, per proposal.md.
- No UI/API surface change to how a course owner adds/removes a collaborator, beyond the storage/enforcement mechanism underneath `service_collaborators_bulk.go`/`handler_instructor.go`.
- No change to any other resource type (Taxonomy, Quiz, etc.) — Course is the only `PolicyProvider` this change registers.

## Decisions

**Decision: the course owner is a synthesized grant, not a stored role-binding row.**

`CoursePolicyProvider.Evaluate` (or an equivalent step before the grant lookup) checks `courses.owner_user_id == principal.ID` first and, if true, returns `PolicyAllow` directly (mirroring how `Authorizer.decidePreparedAuthorization` already treats `providerDecision.Effect == PolicyAllow` as an immediate allow, before ever consulting grants). This avoids writing/maintaining a role-binding row every time a course is created or transferred, and matches today's behavior exactly (owner access is derived from `courses.owner_user_id`, never from a `course_collaborators` row).

Alternative considered: insert an OWNER role-binding row (`resource_id = course.id`) at course-creation time. Rejected: adds a write (and a transfer-of-ownership edge case: the binding must move with `owner_user_id`) for no behavioral gain, since the provider-level check is exactly as immediate and needs no extra state.

**Decision: `requireCourseAccess`/`requireEditorAccess`/`requireOwnerAccess` collapse into one call to `Authorizer.Authorize` per action, not one "what's my role" lookup.**

Today's three functions answer "what access level does this user have," then callers branch on that level. The replacement answers "may this user perform action A on this course," once per call site, via `Authorizer.Authorize(ctx, AuthorizationRequest{Principal, Action: A, Resource: {"course", courseID}})`. Every existing call site names the specific action it's actually gating (e.g. `course_outline:update`, `course_collaborators:manage`) instead of asking for a coarse EDITOR/OWNER tier. This is the one seam: only this helper constructs an `AuthorizationRequest`; every other file passes it an action name.

Alternative considered: keep a `requireEditorAccess`/`requireOwnerAccess`-shaped API but implement it by asking the role gate "does this principal hold role EDITOR/OWNER." Rejected: this is exactly the role-name-comparison pattern the proposal forbids, just moved one layer down: it still gates on "which role" instead of "which action," and would need updating every time an action's ownership requirement changes instead of being a data change in `authorization_role_actions`.

**Decision: `authorization_role_bindings.resource_id = '*'` is a reserved sentinel, enforced by convention plus a `CHECK` constraint, not a schema column.**

Real resource IDs in this codebase are UUIDs; `'*'` can never collide with one. A `CHECK (resource_id = '*' OR resource_id ~ '^[0-9a-f-]{36}$')`-style constraint (or simpler: just documented convention plus the query-side `OR resource_id = '*'`) keeps the column meaning obvious to a reader without adding a new boolean "is_wildcard" column. `roleExpandedGrants`'s `WHERE rb.resource_id = ?` becomes `WHERE (rb.resource_id = ? OR rb.resource_id = '*')`; the index `idx_authorization_role_bindings_decision (principal_user_id, resource_type, resource_id)` still serves both lookups (an equality lookup for `resource_id = '*'` is just another indexed value).

Alternative considered: a nullable `resource_id` meaning "wildcard." Rejected: the column is `NOT NULL` today, and "meaning conveyed by nullness" is exactly the kind of ambiguous-column-meaning cost this module's history has repeatedly chosen against (see `authorization-schema-final-design` decision history). A concrete sentinel value keeps the column's type and non-null constraint unchanged.

**Decision: role-binding management (`authorization/role-binding-management`) lives in `internal/authorization/application` as a new service, mirroring `GrantService`'s shape, not as a method bolted onto `GrantService` itself.**

`GrantService` today manages direct per-action `authorization_grants` rows. A `RoleBindingService` (assign/revoke) manages `authorization_role_bindings` rows, using the same `CanManageGrants` authorization pattern per resource. Kept separate because the two write different tables with different validation rules (a role binding has no `action_name`/`conditions`/`valid_from`/`expires_at` at all, per the existing role-gate design's deliberate simplicity).

Alternative considered: extend `GrantService.ReplaceMany`-style methods to also accept a role binding shape. Rejected: `GrantReplacement`'s fields (`Effect`, `Conditions`, `ValidFrom`, `ExpiresAt`) don't apply to a role binding, and forcing them to share a method signature reintroduces the "dual-purpose row/request" ambiguity this module's history has already rejected once.

**Decision: `RoleBindingService`'s assign and revoke methods take a batch of principal IDs (`PrincipalUserIDs []string`), not one principal per call, mirroring `GrantReplacement`'s existing shape.**

Per `.ai/skills/logic-n-1-optimize/SKILL.md` (applicable to this change, see task 0.2): a caller that needs to affect many principals must never be forced into one call per principal. `service_collaborators_bulk.go`'s existing bulk endpoint already accepts `user_ids []string` in one request; `RoleBindingService.Assign(ctx, RoleBindingAssignment{PrincipalUserIDs, RoleName, Resource, GrantedByUserID})` and `.Revoke(ctx, RoleBindingQuery{PrincipalUserIDs, RoleName, Resource})` accept the same shape so that endpoint's one HTTP request becomes one `RoleBindingService` call, not N. The repository layer inserts/updates all rows in one batched statement (matching `grantInsertBatchSize`/`CreateInBatches` already used by `GormGrantRepository`), not a loop issuing one query per principal.

Alternative considered: a single-principal method, with the bulk endpoint looping over it. Rejected: violates the batch-API skill directly (N single-item calls instead of one batch call) and reintroduces the N+1 query pattern `GrantReplacement`/`ReplaceMany` already avoids for direct grants.

**Decision: Course's collaborator write flows (`service_collaborators_bulk.go`, `handler_instructor.go`) call the new `RoleBindingService`, and `course_collaborators` becomes read-only (then removed) rather than being written in parallel.**

Writing to both tables during a transition window would reintroduce exactly the "two sources of truth" risk. Instead: cut over reads first behind the seam (course_collaborators still the source of truth, but only read through it inside the one seam if needed as a bridge), then cut over writes, then backfill, then drop `course_collaborators` — see Migration Plan.

**Decision: the legacy data importer (`internal/appcli/import_legacy_data_pipeline.go`/`import_legacy_data_rewrite.go`) re-targets `course_collaborators` rows onto `authorization_role_bindings` via a special case, not the generic per-table insert path.**

`importLegacyStatement` builds `INSERT INTO <table> (<cols>) VALUES (...)` using the *source dump's* table name (`st.Table`) and column names (`st.Columns`) directly — `newRow[c]` is only read for columns already present in the source statement. This means the existing per-table `legacyRewriteHandler` functions (including `rewriteCourseCollaborators`) can only change **values**, never the destination table or column names. Since `authorization_role_bindings`'s columns (`principal_user_id`, `role_name`, `resource_type`, `resource_id`, `revoked_at`) don't match `course_collaborators`'s (`course_id`, `user_id`, `role`, `deleted_at`) at all, retargeting requires a dedicated branch: when `st.Table == "course_collaborators"`, skip the generic column-passthrough path entirely and build the `authorization_role_bindings` insert directly, with:
- `principal_user_id` = remapped `user_id` (existing `users` ID map, via `remapRequired`)
- `resource_id` = remapped `course_id` (existing `courses` ID map)
- `resource_type` = the literal `"course"`
- `role_name` = the legacy row's `role` value, **except rows where `role == "OWNER"` are skipped entirely** (report as a skipped row, matching migration `000036`'s backfill rule: owner access is synthesized from `courses.owner_user_id`, never a stored binding)
- `revoked_at` = the legacy row's `deleted_at` (a soft-deleted legacy collaborator becomes an already-revoked binding, not an active one)
- `granted_by_user_id` = `NULL` (the legacy schema never recorded who granted a collaborator role, so this is unknown for every imported historical row, same as migration `000036`'s backfill)

Alternative considered: generalize `importLegacyStatement` itself to support a per-table target-table/column-rename override, so the mapping lives declaratively next to the other `legacyTableRewriters` entries. Rejected for this change: it would touch the shared code path used by all ~30 other supported legacy tables for the sake of one table's special shape, a wider blast radius than a contained special case for the one table that actually needs it.

## Risks / Trade-offs

- [Risk] Collapsing three access-level helpers into one action-level call means every existing call site must be re-audited to name the correct action, instead of a coarse tier. A missed or wrong action name is a silent authorization bug. → Mitigation: enumerate every current call site of `requireCourseAccess`/`requireEditorAccess`/`requireOwnerAccess` before touching any of them (tasks.md), and keep OWNER/EDITOR's *effective* permissions identical to today during cutover so behavior is testable against the existing test suite unchanged.
- [Risk] The wildcard sentinel is a convention enforced by a `CHECK` constraint and query logic, not the type system — a future write path that forgets the `OR resource_id = '*'` branch would silently under-grant. → Mitigation: the wildcard match lives in one place (`roleExpandedGrants`), covered by a unit test asserting both branches; no other query path is expected to need it in this change.
- [Risk] Re-registering Course as a `PolicyProvider` repeats the exact integration this codebase already reverted once. → Mitigation: this design's one-seam decision is the specific fix for the reason it was reverted (complexity spread across ~19 files) — task breakdown must verify no second call site talks to `Authorizer` directly.
- [Risk] Dropping `course_collaborators` before every read path (listing, instructor-candidate exclusion) has been re-pointed at `authorization_role_bindings` breaks collaborator listing UI silently. → Mitigation: tasks.md sequences read-path migration and a passing test for `ListCollaborators`/`ListInstructorCandidates` before the drop migration is written.
- [Risk, found during implementation, fixed post-`/code-review`] `RoleBindingService` could not participate in `internal/course`'s GORM transactions: `internal/authorization`'s `GormGrantRepository` owns its own `*gorm.DB` handle (constructed once at wiring time), not the caller's `tx`. This is the exact cross-repository transaction contract a prior, reverted design built and then removed "until a real production caller exists" — this change is now that caller. Initially mitigated only partially (course-side validation ran in one transaction, then `RoleBindingService` was called sequentially after it committed). A `/code-review` pass then confirmed `wireAuthorization`/`wireCourse` actually share one `*gorm.DB` (no separate connection), so the two-transaction split was never a genuine cross-database limitation. → **Fixed**: `internal/shared/gormx/tx_context.go` (`WithTx`/`DBFromContext`) lets a repository that only receives a `context.Context` join the caller's transaction; `GormGrantRepository.dbForContext` now checks it first. `AddCollaboratorsBulk`/`RemoveCollaborator`/`DeleteCourse`/`PermanentDeleteCourse` now call `RoleBindingService` from inside their course-side transaction via `gormx.WithTx(ctx, tx)`, so the whole operation commits or rolls back atomically.
- [Risk, found by `/code-review`, fixed] Three course/infra read sites (`collaboratorsSelectSQL`'s UNION, `ListEditableCourses`'s `LEFT JOIN`, `existingActiveCollaboratorBindings`'s `Table("authorization_role_bindings")`) hand-wrote SQL directly against `authorization_role_bindings`, contradicting `RoleBindingRepository`'s own doc comment that the table is read back only through `GrantRepository.ListActive`'s role-expansion. → **Fixed**: added a proper read path, `RoleBindingRepository.ListRoleBindings`/`RoleBindingService.List` (for display/listing, distinct from `ListActive`'s role-expansion used for authorization decisions), and re-pointed all four call sites (the three above, plus `instructorCandidatesBaseSQL`'s exclusion subquery) to fetch their (small, resource- or principal-scoped) id/role set through it instead of querying the table directly. A static test (`TestCourseInfraSQLNeverReferencesAuthorizationRoleBindingsDirectly`) guards the two remaining SQL string constants.
- [Risk, found during implementation] `internal/appcli`'s legacy data importer (`import_legacy_data_rewrite.go`/`import_legacy_data_pipeline.go`, live-wired from `main.go`, gated behind `CLI_IMPORT_LEGACY_DATA`) still targets `course_collaborators` and is confirmed still in active future use — outside `internal/course/**`, so it would not be caught by a grep scoped there, and dropping the table without fixing it would silently break the next legacy import. → Mitigation: special-cased, not generalized (see the dedicated Decision above), to avoid widening the blast radius to the ~30 other tables the same generic import path already supports.

## Migration Plan

1. Add `authorization_role_bindings`'s wildcard support (`CHECK` constraint note + `roleExpandedGrants` query change) and the new `RoleBindingService` write path — pure additions to `internal/authorization`, no behavior change to Course yet.
2. Seed `authorization_role_actions` with today's OWNER/EDITOR action sets for `resource_type = 'course'`.
3. Implement `CoursePolicyProvider`, register it in `internal/server/wire.go`/`wire_course.go`.
4. Collapse `repo_access.go`'s three helpers into the one `Authorizer`-backed seam; update every call site to name its actual action. Existing Course test suites must keep passing with identical outcomes.
5. Backfill: one-time script/migration inserting an `authorization_role_bindings` row per active `course_collaborators` row (dev data only, 25 rows today). **In practice this had to run before step 4**, not after: flipping the access-check switch before the role_bindings data exists would deny every existing EDITOR collaborator.
6. Re-point `ListCollaborators`/`instructorCandidatesBaseSQL` reads at `authorization_role_bindings` (joined to `users` as today).
7. Re-point `service_collaborators_bulk.go`/`handler_instructor.go` writes at `RoleBindingService`.
7a. Re-point `internal/appcli`'s legacy data importer's `course_collaborators` handling onto `authorization_role_bindings` (see the dedicated Decision above), so a future legacy import does not depend on the table this change is about to drop.
8. Once reads and writes are fully cut over (including the legacy importer) and verified in dev, migration to drop `course_collaborators`.
9. Run `go build ./...`, `go vet ./...`, `make check-all` after each of steps 1, 4, 7, 7a, 8 at minimum.

Rollback: each step above is independently revertable via a plain revert until step 8; step 8 (dropping `course_collaborators`) is the only step that isn't trivially reversible and is deliberately last, gated on dev verification per proposal.md.

## Open Questions

- Should `authorization_role_bindings.resource_id`'s `CHECK` constraint enforce the UUID-or-`'*'` shape, or is a code comment sufficient given `internal/authorization`'s existing style of enforcing structure at the database level (composite FKs) rather than in application code? Doesn't change the spec or task breakdown either way — can be decided during implementation of task 1. **Resolved during implementation**: a `CHECK` constraint was added (migration `000035`), since this dev DB had already applied migration `000034` (so it could not be edited in place — a new migration was required regardless, making the stricter option effectively free).
- Before dropping `course_collaborators` (task group 6): `internal/appcli/import_legacy_data_rewrite.go`'s `rewriteCourseCollaborators` (wired live from `main.go`) still writes to `course_collaborators` and would break once the table is dropped. This is outside `internal/course/**`, so a grep scoped to that directory would not catch it. **Resolved**: confirmed still in active future use (not retired), so the importer is reworked, not left broken — see the new "Decision: legacy importer re-targets course_collaborators rows onto authorization_role_bindings" below.
