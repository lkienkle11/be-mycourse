## Why

`internal/authorization` ("aws iam fake") today can only grant an action to one principal on one resource instance at a time (`authorization_grants`, keyed by `principal_user_id` + a single `action_name`). There is no concept of "principal P holds a named role R on resource X" that expands to a bundle of actions, so giving someone a bundle (e.g. what "collaborator" or "reviewer" means for a course) requires writing one grant row per action, and redefining that bundle later (adding or removing an action from what it covers) requires backfilling every existing holder's grant rows across every resource instance. That backfill was a real, recurring cost during the Course collaborator work this branch already reverted (`revert-course-authorization-extension`), and the user expects to redefine such bundles every few weeks to a few months, not rarely — making the backfill cost a recurring operational burden worth removing now, before any resource type is reintroduced.

Note on "new" throughout this document: nothing in `internal/authorization` — including `authorization_actions` and `authorization_grants` themselves — has ever been applied to a database or committed (still `??` untracked, confirmed repeatedly across sessions). "New table" below means a table introduced specifically for the role-bundle capability, on top of the two the generic engine already carries in its current uncommitted state. The comparison that matters for maintainability is the **absolute total table count** across the whole (still entirely uncommitted) module.

This design went through five iterations before landing on the one that shipped:
1. Two additional tables (`authorization_resource_roles`, `authorization_resource_role_actions`) with no relationship to the existing action catalog — built, then reverted: looked like isolated, bolted-on schema. Total module table count: 4.
2. Two additional tables with real foreign keys into the existing action catalog (`authorization_role_actions`, `authorization_role_bindings`) — built, tested, `make check-all` passing, then reverted a second time (this specific revert was done without waiting for the user's explicit go-ahead, which the user rightly pushed back on; see `.context/session-e56de0bc-...md` for the full account) after further review flagged that it still meant four tables and two "role" concepts (this one, and the pre-existing global `roles` table) for a module with zero current consumers. Total module table count: 4.
3. A role stored as a named value in the existing `action_name` column of `authorization_grants` (no schema change to that table), resolved against a new `role_names` array on the existing `authorization_actions` catalog. Built, tested, `make check-all` passing on the first attempt. Total module table count: 2. Rejected on further review: while `authorization_grants`'s schema never changes, the *meaning* of its `action_name` column becomes context-dependent — sometimes a concrete action, sometimes a role reference — with no schema-visible marker distinguishing the two. That is a real, if differently-shaped, complexity cost (values with ambiguous meaning, rather than more tables), and the user weighed it against option 2's cost (more tables, but every table and column has one unambiguous meaning) and chose explicit schema-level clarity over fewer tables, for now.
4. **This is the design that shipped — the same shape as iteration 2, reinstated deliberately after the trade-off in iteration 3 was made explicit and compared side by side.** Two tables, each with a real foreign key into existing schema: `authorization_role_actions (role_name, resource_type, action_name)` FK'd via the exact composite-FK shape `authorization_grants` already uses against `authorization_actions`, and `authorization_role_bindings (id, principal_user_id, role_name, resource_type, resource_id, granted_by_user_id, created_at, revoked_at)` FK'd to `users` like `authorization_grants` already is. Total module table count: 4. Chosen explicitly as "let's try this for now" — table count is higher than iteration 3, but every row in every table has exactly one, schema-visible meaning; nothing needs a reader to know an unwritten convention about what a column's value might mean depending on context.

## What Changes

- New generic decision input: a **resource-scoped role binding** — "principal P holds role name R on resource (type, id)" — that expands to whichever actions role R currently covers, so redefining a role's action set takes effect immediately for every existing holder, with no backfill.
- Two additional tables (on top of the two the module already has), added to the still-unapplied `migrations/000034_authorization_base.up.sql`/`.down.sql` (not a new migration file — that migration has never run against any database):
  - `authorization_role_actions (role_name, resource_type, action_name, created_at)`: the role definition — which actions a role name currently covers, for a resource type. `PRIMARY KEY (role_name, resource_type, action_name)`, with `FOREIGN KEY (action_name, resource_type) REFERENCES authorization_actions (action_name, resource_type)` — the exact same composite FK shape `authorization_grants` already uses against the same table. A role can never reference an action that is not already registered; this is enforced by the database.
  - `authorization_role_bindings (id, principal_user_id, role_name, resource_type, resource_id, granted_by_user_id, created_at, revoked_at)`: the role binding — who holds which role on which specific resource instance. `principal_user_id`/`granted_by_user_id` are real foreign keys to `users`, matching `authorization_grants`'s existing shape.
- **`authorization_grants` and `authorization_actions` are not modified at all** — no new columns, no relaxed constraints, no `CHECK` constraints. Every existing row, every existing write path (`Create`, `ReplaceMany`, `UpsertActions`), and every existing test continues to work completely unchanged.
- `GormGrantRepository.ListActive` is extended with a second query that joins active role bindings to their role's current actions, producing synthesized `ALLOW` grants merged with the directly stored ones, before returning. Both `Authorizer.Authorize` (mutation gate) and `EffectiveActionProjector.Project` (read-side effective-action listing) see role-expanded access automatically, with **zero changes to `Authorizer`, `GrantService`, `EffectiveActionProjector`, or `Registry`**, and — because `authorization_grants`'s schema and every existing `GormGrantRepository` write method are untouched — **zero changes to any existing write method either**. Every other decision rule (global boundary permission check, provider hard-deny/allow, explicit `DENY` always wins) is unchanged and applies identically whether a matched grant is stored directly or synthesized from a role.
- **Scope cut, explicit**: this change ships only the gate (schema + read-path expansion used by the decision engine). It does **not** add any service, HTTP route, or authorization check for *managing* role bindings or role-action membership (no "who can assign a role" / "who can redefine a role's actions" flow) — that governance is deliberately out of scope until a real requirement for it exists. Test fixtures write the two new tables directly; no new production write path is added in this change.
- Not resource-specific: implemented entirely inside `internal/authorization`, with no dependency on Course, Taxonomy, or any other domain package, so it is available to any future `PolicyProvider` the moment one registers.

## Capabilities

### New Capabilities

- `authorization/resource-scoped-role-gate`: a principal can hold a named role on a specific resource instance, and the role's current action set — defined in its own table, independent of any single holder — is honored by the same decision path as a direct grant, without a management API for assigning roles or editing role-action membership in this change.

### Modified Capabilities

None. No spec currently exists for `internal/authorization`'s direct-grant decision path either (`openspec/specs/` has no `authorization/*` capability yet), so this is additive, not a delta on documented behavior.

## Impact

- `migrations/000034_authorization_base.up.sql` / `.down.sql`: two new `CREATE TABLE` statements + one partial index, added to the existing, still-unapplied migration (no new migration number). No seed data. Module total table count: 4.
- `internal/shared/constants/dbschema_name.go`: two table-name constants (`TableAuthorizationRoleActions`, `TableAuthorizationRoleBindings`).
- `internal/authorization/infra/gorm_repository.go`: two new unexported row types for the new tables, a small row type for the join result, a new private method computing role-expanded grants, and a pure merge helper combining direct + role-expanded results into `ListActive`'s return value. `grantRow`, `grantToRow`, `rowToGrant`, and every existing method are **unchanged**.
- `internal/authorization/domain/authorization.go`: a doc comment on `GrantRepository.ListActive` noting it may return grants synthesized from resource-scoped roles in addition to directly stored ones. No type or interface signature changes.
- `docs/modules/authorization.md`: a section describing the resource-scoped role gate, the two tables, and the explicit "no management API yet" scope boundary.
- No changes to `Authorizer`, `GrantService`, `EffectiveActionProjector`, `Registry`, or any `PolicyProvider`.
- No changes to any Course, Taxonomy, or other domain package (none are registered as `PolicyProvider`s right now, per `revert-course-authorization-extension`).
- Tests: new unit tests for the merge helper (pure function, no DB) and for the new row types' mapping behavior, following the existing pattern in `gorm_repository_test.go` (no live Postgres harness available in this environment).
