## Why

`course_collaborators` (`course_id`, `user_id`, `role`) is Course's own, hand-rolled access-control table: every mutation entry point that needs to know "can this user manage this course" reads `course_collaborators.role` and branches directly on the role string (e.g. `internal/course/infra/repo_access.go:263`, `if access.Role != domain.CollaboratorRoleOwner`). Meanwhile `internal/authorization` already ships a generic, resource-scoped role gate (`authorization_role_actions` + `authorization_role_bindings`, migration `000034`, committed in `19fc149`, fully wired into `Authorizer`/`EffectiveActionProjector` via `GormGrantRepository.roleExpandedGrants`/`mergeGrants`) that lets a role's action set be redefined once and take effect for every existing holder instantly, with zero backfill. Course is expected to need more roles beyond OWNER/EDITOR soon; extending `course_collaborators.role` today means another hardcoded branch per new role, exactly the cost the generic engine exists to remove.

A prior attempt to wire Course into this engine was built and then reverted (`revert-course-authorization-extension`) because the integration spread role-check logic across roughly 19 files with no single seam. This change re-attempts the integration deliberately, this time behind one access-check seam, and only after the generic engine had time to land and prove itself on its own (it has: implemented, migrated, currently 0 rows, zero other consumers).

## What Changes

- **BREAKING**: Course access checks stop reading `course_collaborators.role` directly. `requireCourseAccess`/`requireEditorAccess`/`requireOwnerAccess` (`internal/course/infra/repo_access.go`) collapse into a single seam that calls `Authorizer.Authorize` for an action-level decision; nothing else in `internal/course` is allowed to branch on a role name string. This is a hard rule for this change, not just for this file: no code path anywhere may gate a decision on `role_name`/`Role ==` comparisons. A role is only ever a bundle of actions resolved through `authorization_role_actions`.
- Register Course as a `PolicyProvider` (`CoursePolicyProvider`) in `internal/authorization`'s `Registry`, declaring Course's actions (equivalents of today's OWNER-only vs. any-collaborator operations) with `resource_type = "course"`.
- Seed `authorization_role_actions` with the current OWNER/EDITOR action sets for `resource_type = "course"`, matching today's behavior exactly (no behavior change for existing collaborators on cutover; only the enforcement mechanism changes).
- Add a resource-scoped **wildcard** to the existing role-binding read path: `authorization_role_bindings.resource_id` gains the reserved sentinel value `'*'`, meaning "every resource of this binding's `resource_type`" (e.g. every course). No new column, no new table. `GormGrantRepository.roleExpandedGrants`'s resource filter changes from a strict `rb.resource_id = ?` to `rb.resource_id = ? OR rb.resource_id = '*'`. Scope is per `resource_type`, not cross-type or global; global-scope permission checks continue to use the existing, separate `GlobalPermissions` JWT-claim gate in `Authorizer.preflight`.
- Add a **role-binding management write path** (assign/revoke a role binding for a principal on a resource, or on `'*'`) inside `internal/authorization`. This capability does not exist yet — the original role-gate proposal explicitly scoped it out (read-side only). Course's collaborator add/remove/change-role flows (`service_collaborators_bulk.go`, `handler_instructor.go`) call this instead of writing `course_collaborators` rows directly. Assignment/revocation accept a **batch** of principal IDs per call (never one call per principal — per `.ai/skills/logic-n-1-optimize`).
- Migrate the 25 existing dev-only `course_collaborators` rows into `authorization_role_bindings` via a one-time backfill (dev data only; production has a different dataset and is out of scope for this change's migration plan).
- Re-point `internal/appcli`'s legacy data importer (`import_legacy_data_rewrite.go`/`import_legacy_data_pipeline.go`, live-wired from `main.go` via `MaybeRunImportLegacyData`, gated by `CLI_IMPORT_LEGACY_DATA`) so a future import of a legacy `course_collaborators` dump lands in `authorization_role_bindings` instead. Found during implementation (task group 6): this importer still targets `course_collaborators` and is confirmed still in active future use, not retired — dropping the table without fixing it would break the next legacy import.
- Drop the `course_collaborators` table once every read and write path has moved to the role gate and the backfill is verified.

## Capabilities

### New Capabilities
- `authorization/role-binding-wildcard`: a resource-scoped role binding may target `resource_id = '*'` to mean every resource of that binding's `resource_type`, honored identically to a concrete resource ID by the existing decision/read path.
- `authorization/role-binding-management`: assign and revoke a resource-scoped role binding (principal, role, resource type, resource ID or `'*'`) through `internal/authorization`, with no resource-type-specific code required.
- `course/collaborator-role-gate`: Course registers as a `PolicyProvider` and every Course access check resolves through `Authorizer` (action-level, role-expanded) instead of reading `course_collaborators.role` directly.

### Modified Capabilities
(none — `openspec/specs/` has no existing capability for `internal/authorization`'s decision path or for Course collaborator access yet, so this is additive only)
